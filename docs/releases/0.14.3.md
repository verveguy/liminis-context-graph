# 0.14.3 — 2026-09-15 (full release notes)

Windows becomes a supported platform, and hybrid search returns ranked results instead of
insertion-ordered ones. **There is no database migration in this release**, and `lbug` stays
pinned at 0.18.1 — see "Why lbug is still 0.18.1" below, which is the most important thing here
for anyone tracking the upgrade.

### Upgrading

Nothing to do. No storage migration, no API change, no configuration change. A 0.14.x workspace
opens unchanged.

Windows users: see Prerequisites.

## Windows support

`lcg-service` now builds and runs on Windows x64.

**Transport.** Windows has no Unix domain socket, so the service serves a **named pipe**. The
design is not a thin substitute — it carries its own access control:

- every pipe instance gets a protected DACL granting only the service's own user and SYSTEM. This
  matters because the *default* pipe DACL grants Everyone read access;
- remote clients are refused;
- the first instance is created with `FILE_FLAG_FIRST_PIPE_INSTANCE`, so another process can
  neither squat the name nor silently join as a second server.

**Discovery.** The service writes its pipe name to `.lcg/service.endpoint`, so clients in other
languages can find it without hardcoding the naming scheme.

**Shutdown.** Windows console-control events drive the same clean-shutdown path `SIGTERM` drives
elsewhere.

**OpenSSL.** Linked **statically** into the executable. This is a deliberate Windows-only
exception to ADR-0550, which keeps OpenSSL dynamic on macOS and Linux: a release archive cannot
carry DLLs for one target without carrying them for all, and no Windows package manager would
patch a DLL we shipped. The consequence is worth stating plainly — **an OpenSSL CVE fix requires a
new lcg release on Windows**, whereas macOS and Linux pick it up from the system.

Separately, lbug's own `vector` and `fts` extensions import OpenSSL dynamically, so the two DLLs
they need are bundled beside them in the release archive and put on the DLL search path at load
time. Without that, the extensions fail to load on any machine that does not happen to have
OpenSSL on `PATH`. See [ADR-0581](../adr/0581-windows-static-openssl.md).

### Prerequisites

**The Microsoft Visual C++ Redistributable (x64, 2015–2022) must be installed.** It is not
bundled. Most machines have it; without it the executable fails to start with a standard Windows
loader error, before any lcg code runs.

### What was verified, and what was not

On lbug 0.18.1, lcg was verified on one Windows 11 Pro x64 machine (with the Visual C++ 2015–2022
runtime present, and no OpenSSL DLL reachable on `PATH`): the **published 0.14.3
`x86_64-pc-windows-msvc` artifact**, downloaded from this release and checksum-verified, together
with a local build, started the named-pipe service, loaded the bundled vector and FTS
extensions, created and queried vector and full-text indexes, ranked all four semantic queries
correctly with `bge-base-en-v1.5` embeddings with neither `LCG_LBUG_HOME` nor `LBUG_HOME` set — so the bundled
extensions were resolved beside the executable — and opened, reopened and WAL-rebuilt an existing
0.18.1 database; the named-pipe service e2e tests and a downstream consumer's test suite also
passed there.

Deliberately **not** claimed:

- **A pristine machine.** No machine without the VC++ runtime was tried.
- **The PowerShell installer end to end.** The zip was extracted by hand.
- **Other environments.** Windows 11 only — no Windows 10, no ARM64, one machine.
- **Endurance.** No long-running, concurrent-load or multi-client testing beyond the e2e suites.
- **Unusual paths.** No Unicode or long-path (>260 character) workspace directories.

### Clients

Downstream consumers need a client that reads `.lcg/service.endpoint` to locate the pipe. `orac`
has one; the Liminis app and `liminis-framework` do not yet.

## Ranked search results

`knowledge_find_entities` and `knowledge_find_relationships` fetch their rows with a Cypher
`WHERE uuid IN $uuids` lookup, which carries no `ORDER BY`. Rows therefore came back in storage
order, **discarding the RRF-fused ranking computed immediately beforehand**. The correct top-k set
was returned, in an effectively arbitrary order.

Results now follow the fused ranking. If you have been ranking or truncating lcg search results
downstream, or concluded that lcg's relevance ordering was poor, this is why. (#584)

## Bundled extensions and symlinks

0.14.2 began shipping lbug's vector and FTS extensions inside the release archive so startup never
contacts a third-party CDN. On macOS and Windows, `std::env::current_exe()` reports the path the
process was *launched as*, so launching through a stable symlink into a versioned install resolved
the bundle against the symlink's directory, missed the real `.lbdb` tree, and silently fell back to
downloading — with no error. The executable path is now canonicalized before the bundle is
resolved. (#583)

## Why lbug is still 0.18.1

This release was intended to carry the `lbug` upgrade to 0.20.4, with its one-way storage
migration (42 → 47) — which is why it was originally numbered 0.15.0. The upgrade has been
**deferred to 0.15.0**, because the published Windows extension binaries for the entire lbug
0.20.x line crash the process. With no migration and no breaking change left in it, this release
is a patch.

Established by bisection on Windows 11 x64, using LadybugDB's own `lbug.exe` with no lcg code
involved:

| lbug | Windows x64 |
|---|---|
| 0.18.1 | works — extensions load, indexes create and query |
| 0.19.0 | works |
| 0.20.0 | access violation **inside** `libvector` / `libfts` during `LOAD EXTENSION` |
| 0.20.4 | loads, then access violation at `CREATE_VECTOR_INDEX` / `CREATE_FTS_INDEX` |

Both the vector and full-text extensions are affected, and there is no workaround available to us:
extension artifacts are published per **minor**, so every 0.20.x patch release loads the same
v0.20.0 binaries. Pinning 0.20.0 is not an escape either — it is one of the releases carrying an
unrelated upstream SIGSEGV that the 0.20.4 upgrade was meant to pick up a fix for.

Rather than ship the upgrade on Linux and macOS while holding Windows back, the upgrade waits, so
all four platforms move together. The upgrade work itself is complete and tested on Linux and
macOS; it is pinned, rebased and ready for whenever the upstream extension builds are fixed.

**On Linux and macOS, 0.14.3 runs the same lbug 0.18.1 that 0.14.0 through 0.14.2 shipped**, so
this deferral changes nothing about what you are already running.
